## 해결하려는 문제

부모님과 따로 사는 20~30대 88명을 설문한 결과, 67.1%가 부모님의 질병이나 병원 방문을 뒤늦게 알게 된 경험이 있었다. 기존 건강관리 앱은 꾸준히 기록하기 어렵고, 자녀가 일방적으로 부모님을 지켜보는 방식은 부모 세대에게 감시로 느껴진다.

온담은 가족이 **서로의** 기록을 확인하는 양방향 구조로 기록을 이어 가게 하는 것을 목표로 했다.

## 내가 한 일

- **API 20여 개 설계·구현**: 아침 공통 질문, 저녁 건강 체크, 일지, 주간 리포트(가족용 포함), 음성 편지, 검진 일정
- **AI 기능**: 지병 기반 맞춤 질문(실패 시 질환별 템플릿으로 대체), 주간 리포트 코멘트, 30일 누적 증상 기반 진료 질문 추천, 음성 입력(STT)
- **인프라**: EC2·RDS·S3 구성, Nginx 리버스 프록시와 HTTPS, 환경변수 기반 시크릿 관리

   ▼

│     │            │              15초 타임아웃         │    (GPT · Whisper)
│     │ 트랜잭션 안 │                                   │

원칙은 하나였다. **DB 저장은 트랜잭션 안에서 끝내고, 통제할 수 없는 외부 AI 호출은 트랜잭션 밖에서 시간 상한을 두고 실행한다.** 이 원칙은 처음부터 있던 것이 아니라 아래 문제들을 겪으며 세운 것이다.

## 트러블슈팅

### ① 폴백이 숨긴 장애

**문제**: 프론트엔드에서 "저녁 맞춤 질문이 매일 같다"는 제보가 들어왔다.

**원인**: 재배포 과정에서 API 키 환경변수가 빠져 GPT 호출이 실패하고 있었다. 맞춤 질문 생성이 실패하면 질환별 템플릿 문구로 대체하도록 폴백을 만들어 두었는데, 이 대체 문구가 조용히 노출되고 있었다. 더 큰 문제는 대체 문구와 정상 생성 결과가 같은 형태로 저장되어, DB만 봐서는 둘을 구분할 수 없었다는 점이다.

**해결**: GPT 클라이언트와 예외 처리 경로에 응답 본문 로깅을 추가해 원인을 확인하고 키를 교체했다.

**결과**: 맞춤 질문이 정상적으로 생성되기 시작했고, 이후로는 폴백이 동작하면 로그가 남아 같은 장애를 로그만으로 식별할 수 있게 됐다.

**배운 점**: 폴백은 사용자 경험을 지키기 위한 장치지만, 동시에 장애를 숨긴다. 서비스는 계속 돌아가는 것처럼 보이기 때문에 아무도 이상을 눈치채지 못한다. **폴백이 동작하면 반드시 흔적이 남아야 한다.**

이 경험은 이후 화이트햇 스쿨 프로젝트에서 "정책은 Ready인데 실제로는 막지 못한" 문제를 만났을 때 다시 떠올랐다. 겉으로 정상인 상태가 실제 동작을 보장하지 않는다는 점에서 같은 문제였다. ([관련 글](/posts/kyverno-ready-but-not-enforcing/))

### ② 외부 AI 지연이 서버 전체를 막지 않도록

**문제**: GPT와 Whisper 호출에 타임아웃이 없었다. 게다가 답변 제출 트랜잭션 안에서 GPT를 2~3회 호출하고 있었다.

왜 문제가 되는지 정리하면 이렇다. `@Transactional` 메서드는 시작부터 끝까지 DB 커넥션 하나를 붙잡는다. 그 안에서 응답이 느린 외부 API를 호출하면, DB 작업은 이미 끝났는데도 AI 응답을 기다리는 동안 커넥션이 반납되지 않는다. 이런 요청이 몇 개만 쌓여도 커넥션 풀이 바닥나고, AI와 전혀 상관없는 다른 API까지 커넥션을 기다리며 멈추게 된다. 외부 서비스 하나의 지연이 서버 전체 장애로 번지는 경로다.

```text
[변경 전]
트랜잭션 시작 ── 저장 ── GPT 호출(대기…) ── GPT 호출(대기…) ── 커밋
└────────────── 이 시간 내내 DB 커넥션 점유 ──────────────────┘

[변경 후]
트랜잭션 시작 ── 저장 ── 커밋        GPT 호출 (최대 15초)
└─ 커넥션 점유 ─┘                    └─ 커넥션과 무관 ─┘
```

**해결**:
- 외부 호출에 15초 타임아웃을 적용했다.
- 저장(`@Transactional`)과 리포트 생성·알림(비트랜잭션)을 메서드 단위로 분리했다.
- 세 곳에 중복되어 있던 STT 호출 코드를 공통 클라이언트로 통합해, 타임아웃과 예외 처리를 한 곳에서 관리하도록 했다.

**결과**: AI 응답이 늦어져도 DB 커넥션을 붙잡지 않는 구조로 바뀌어, 외부 지연이 다른 API로 번지는 경로를 차단했다.

**배운 점**: 통제할 수 없는 외부 호출은 트랜잭션 밖에, 시간 상한과 함께 둔다.

### ③ LLM이 약한 계산은 서버가 대신

**문제**: 주간 리포트에서 GPT가 가장 좋은 값이 나온 금요일을 "가장 낮은 요일"이라고 서술했다.

LLM은 문장을 자연스럽게 만드는 데는 강하지만, 여러 숫자를 비교해 최댓값과 최솟값을 고르는 일은 안정적으로 해내지 못한다. 그럴듯한 문장 안에 틀린 사실이 섞이면 사용자는 오히려 알아채기 어렵다. 건강 정보라면 더 위험하다.

**해결**:
- 서버가 최댓값과 해당 요일을 미리 계산해 프롬프트로 넘기고, "직접 계산하지 말고 인용하라"고 지시했다.
- 프롬프트에 넣은 예시 문장을 GPT가 그대로 모방하는 경향을 확인하고, 어투를 바꾸고 싶을 때는 지시문이 아니라 예시 문장 자체를 바꿔 교정했다.

**결과**: 수치 판단을 서버로 옮겨 리포트 문장의 사실 오류 원인을 제거했다.

**배운 점**: LLM에는 서술을, 서버에는 계산을 맡겨야 정확도가 올라간다.

### ④ 협업: 연동 오류의 원인을 요청 데이터로 규명

**문제**: 프론트엔드 연동 중 `413 Payload Too Large` 오류가 반복됐지만, 백엔드와 프론트엔드 중 어느 쪽 문제인지 판단이 늦어졌다.

**해결**: 요청 payload를 직접 분석해, 같은 값이 1만 건 넘게 반복 전송되고 있다는 것을 확인하고 공유했다. 이후 QA 문서를 백엔드와 프론트엔드 영역별로 분류해, 문제가 생기면 수정 주체가 바로 보이도록 했다.

**배운 점**: "어느 쪽 문제인가"로 시간을 쓰기보다, 실제로 오간 데이터를 먼저 확인하면 논쟁 없이 원인에 도달한다.

## 돌아보며

네 가지 문제 모두 처음 구현할 때는 보이지 않았다. 폴백은 잘 동작했고, 트랜잭션도 정상적으로 커밋됐고, GPT도 문장을 만들어 냈다. 문제는 운영하면서, 혹은 결과를 끝까지 확인했을 때 드러났다.

특히 첫 번째 장애는 환경변수로 관리하던 API 키가 재배포 과정에서 빠지며 시작됐다. 시크릿을 코드에 넣지 않는 것만큼, 배포할 때 시크릿이 제대로 주입되었는지 확인하는 것도 중요하다는 것을 배웠다.
