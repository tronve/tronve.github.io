## 프로젝트 목표

**오픈소스 도구만으로 소프트웨어 공급망 보안 체계를 어디까지 구축할 수 있는지, 그 한계는 어디인지**를 실제 AWS EKS 환경에서 검증하는 것이 목표였다. 진행은 세 단계로 나눴다.

1. 공급망 공격 사례 조사
2. 3계층 보안 아키텍처 설계와 구현
3. 공격 시나리오 실증과 운영 검증

## 1단계: 사례 조사

사례를 나열하는 대신 **공급망의 어느 지점에서 신뢰가 깨졌는지**를 기준으로 8개 사례를 분석했다. 팀원이 한 사례씩 맡았고, 나는 CI 보조 도구가 침해된 Codecov 사례를 맡았다.

| 사례 | 침해 지점 |
| --- | --- |
| Log4Shell | 라이브러리 자체 결함 |
| axios | 간접 의존성 |
| event-stream | 유지보수자 권한 |
| SolarWinds | 빌드 서버 |
| Notepad++ | 배포 인프라 |
| Codecov | CI 보조 도구 |
| LiteLLM | 검증 도구 자체 |
| TeamTNT | 배포 후 런타임 |

결론은 "단일 기술로는 공급망 공격을 막을 수 없다"였다. 대부분의 방어는 완전한 차단이 아니라 조건부 차단이거나 탐지 수단이었다. 예를 들어 SolarWinds처럼 빌드 단계가 뚫리면 변조된 결과물도 정상적으로 서명될 수 있다.

## 2단계: 3계층 방어 구축

한 계층의 빈틈을 다른 계층이 메우도록 방어를 세 계층으로 나눴다.

- **배포 전 (CI)**: GitHub Actions 7개 Job을 순서대로 연결했다. Gitleaks(시크릿), Checkov와 tfsec(IaC), SBOM 비교와 위험도 점수(의존성), Trivy(이미지 취약점) 검사를 통과해야만 ECR에 푸시하고 Cosign으로 keyless 서명한다.
- **배포 시점 (클러스터)**: Kyverno로 서명 검증, `latest` 태그 금지, root 실행 금지 정책을 적용했다.
- **배포 후 (런타임)**: Falco와 Falcosidekick으로 컨테이너 안의 이상 행위를 탐지해 Discord로 알림을 보냈다. TeamTNT 사례를 바탕으로 크립토마이닝, 로그 삭제, 백도어 계정 등의 커스텀 룰을 만들었다.

권한 구조도 다시 설계했다. 처음에는 팀원 전원을 클러스터 관리자 권한에 매핑했는데, 멘토님께서 최소 권한 원칙과 모순된다고 피드백해 주셨다. 그래서 EKS Access Entries와 Terraform으로 팀원별 네임스페이스와 Role을 만들어 각자 자기 네임스페이스에서만 작업하도록 바꿨다. GitHub Actions는 장기 액세스 키 없이 OIDC로 IAM 역할을 받아 ECR에 접근하도록 했다.

## 3단계: 시나리오 11개로 검증

임의로 만든 공격이 아니라 1단계 사례의 행위 패턴을 가져와 시나리오 11개를 만들었다. 실제 악성코드나 외부 C2 서버는 쓰지 않고, 무해한 더미 페이로드와 팀이 통제하는 내부 엔드포인트만 사용했다.

판정은 **설계한 환경에서의 최초 결과**를 기준으로 했고, 고친 뒤의 결과로 바꾸지 않았다. 그 결과 8개는 예측대로 막거나 탐지했고, 3개는 도구가 있었는데도 막지 못했다.

| 시나리오 | 결과 |
| --- | --- |
| 미서명 이미지 배포 | 정책은 Ready였지만 웹훅이 등록되지 않아 통과 |
| 외부 레지스트리 이미지 | 정책이 Audit 모드여서 통과 |
| 휴면 후 사설 IP 연결 | 기본 매크로가 사설 IP를 제외해 탐지 0건 |

세 개 모두 **도구는 설치되어 있었지만 실제로는 작동하지 않았다**는 공통점이 있었다. 첫 번째 사례는 [별도 글](/posts/kyverno-ready-but-not-enforcing/)로 자세히 정리했다.

## 내가 맡은 일

- **PM**: 일정과 회의 총괄, README와 최종 발표
- **하드코딩 시크릿 차단 시나리오**: Gitleaks가 4초 만에 차단했다. 오탐을 줄이려고 넣은 예외 키워드가 실제 시크릿까지 놓치는 문제를 발견해, 위치 기준 매칭으로 바꿔 3건 모두 탐지되도록 했다.
- **자격증명 외부 전송 탐지 시나리오**: 시크릿 경로를 직접 지정한 전송은 CRITICAL로 탐지했지만, 파이프로 넘기면 놓쳤다. Falco 룰이 단일 이벤트 기준이라 "읽은 뒤 보낸다" 같은 순서 기반 행위를 잡기 어렵다는 한계를 확인했다.
- **정책 점검 스크립트**: 상태 표시를 믿지 않고 서버 dry-run으로 실제 거부 여부를 시험하는 스크립트를 만들어, 이틀 사이 실제 이상 2건을 잡았다.
- **권한 문제 수정**: AWS 역할의 신뢰 조건이 모든 브랜치와 PR을 허용해 병합 전 PR 이미지까지 ECR에 올라가 서명받던 문제를 main으로 한정했다. Falco 설치 계정이 모든 네임스페이스의 Secret을 읽을 수 있던 과잉 권한도 회수했다.

## 결론: 도구가 있는데도 구멍이 생긴 이유

구멍은 설치 단계가 아니라 운영 단계에서 생겼다. 팀에서는 그 원인을 다섯 가지로 정리했다.

| 축 | 의미 |
| --- | --- |
| 작동 검증 | 켜져 있다는 표시와 실제 작동은 다르다 |
| 설정 범위 | 도구가 있어도 적용 범위 밖은 비어 있다 |
| 예외 승인 | 예외 장치가 규칙과 어긋나거나 통제되지 않는다 |
| 권한 강제 | 규칙을 만들어도 강제 장치가 없거나 도구 권한이 과하다 |
| 탐지 조건 | 룰의 조건이 좁으면 같은 행위도 놓친다 |

모두 설치할 때는 보이지 않다가 실제로 시험했을 때 드러났다. **도구를 붙이는 것만으로는 방어가 되지 않고, 실제로 작동하는지 시험하는 운영 검증까지 해야 방어가 성립한다**는 것이 프로젝트의 결론이었다.

## PM으로서 돌아보면

- **판정 기준을 먼저 정한 것이 결과를 정직하게 만들었다.** 최초 결과로 판정한다는 원칙이 없었다면, 고친 뒤 통과한 시나리오들을 "성공"으로 기록하고 넘어갔을 것이다. 가장 많이 배운 것은 바로 그 세 개였다.
- **진행 순서도 설계의 일부였다.** 외부 레지스트리 차단 정책을 Enforce로 켜면 런타임 시나리오에 쓸 수신 서버 이미지가 막히기 때문에, 런타임 시나리오를 먼저 하고 클러스터 시나리오를 나중에 진행했다.
- **남이 재현할 수 있게 쓰는 일은 생각보다 어렵다.** 팀원끼리 서로의 스크립트를 문서만 보고 실행하는 교차 검증을 8쌍 진행했는데, 5쌍만 끝까지 실행됐다. 클러스터 쪽 스크립트는 일반 팀원 권한으로 실행할 수 없었고, 그 과정에서 나온 문제들을 다시 고쳐 반영했다.

## 한계와 남은 과제

단일 데모 앱과 단일 클러스터에서 시나리오당 한 번씩 확인했기 때문에, 실제 공격에서의 탐지율을 말할 수는 없다. 또 CI 전체 시간 중 보안 검사가 77.7%를 차지해, 보안과 속도 사이의 비용도 확인했다.

남은 과제는 다음과 같다.

- 파이프 우회처럼 순서 기반 행위를 탐지하는 방법 찾기
- CI 보안 도구 버전을 태그가 아닌 커밋 SHA로 고정하기
- 탐지 후 격리 같은 자동 대응과 관리형 서비스와의 탐지 범위 비교

특히 파이프 우회가 왜 탐지되지 않았는지는 아직 시스템 콜 수준에서 설명하지 못한다. 나이츠 프론티어 기간 동안 직접 파고들어 정리해 볼 계획이다.
