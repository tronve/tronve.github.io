교내 기업 연계 캡스톤으로 **DrimFlow**를 만들고 있다. 사용자가 화면에서 블록을 이어 붙여 업무 흐름을 만들고 실행하는 워크플로 라이브러리다. 호스트 Spring 애플리케이션에 탑재되는 형태이고, 나는 백엔드 세 파트 중 **실행 파트**(실행 명령 API와 실행 엔진)를 맡았다.

아직 진행 중인 프로젝트라, 지금까지 확정한 설계 결정과 그 이유를 중심으로 기록해 둔다.

## 실행 파트 설계 결정

워크플로 엔진은 "한 번 시작한 실행이 어떤 상황에서도 일관된 결과를 내는가"가 핵심이다. 그래서 설계 결정마다 막으려는 문제를 먼저 정했다.

### 실행 API: 버전 스냅샷

**결정**: 실행이 시작되는 시점의 활성 버전을 스냅샷으로 고정한다.

**막으려는 문제**: 실행 도중 누군가 워크플로 정의를 수정하면, 앞쪽 노드는 이전 정의로, 뒤쪽 노드는 새 정의로 실행될 수 있다. 결과가 어떤 정의에서 나온 것인지 알 수 없게 된다. 실행은 시작 시점의 정의에 묶여 있어야 한다.

### 실행 API: 동시 실행 제한

**결정**: 동기 실행은 세마포어로 동시 실행 수를 제한하고, 30초 타임아웃을 두며, 상한을 넘으면 `429 Too Many Requests`로 응답한다.

**막으려는 문제**: 동기 실행 요청이 몰리면 요청마다 스레드와 DB 커넥션을 붙잡고 기다리게 되어, 결국 서버 전체의 스레드와 커넥션이 고갈된다. 처리할 수 있는 만큼만 받고 나머지는 빠르게 거절하는 편이, 모두를 받아 놓고 모두 느려지는 것보다 낫다. 온담에서 외부 AI 지연이 커넥션 고갈로 번질 뻔한 경험이 이 결정에 영향을 줬다. ([관련 글](/posts/ondam-backend-retro/))

### 신호 API: 한 트랜잭션과 유니크 키

**결정**: 신호 저장과 대기 중인 노드의 완료 처리를 하나의 트랜잭션으로 묶고, 유니크 키로 같은 신호의 재수신을 거부한다.

**막으려는 문제**:
- 신호는 저장됐는데 노드는 계속 멈춰 있는 불일치. 둘이 따로 처리되면 그 사이에 실패했을 때 상태가 어긋난다.
- 네트워크 재전송 등으로 같은 신호가 두 번 들어와 다음 단계가 중복 실행되는 것. 유니크 키 제약으로 DB 수준에서 멱등성을 보장한다. 애플리케이션 코드에서 "이미 받았는지" 조회한 뒤 저장하는 방식은 두 요청이 동시에 들어오면 둘 다 통과할 수 있다.

### 취소 API: 노드 경계에서 정지와 보상

**결정**: 취소는 실행 중인 노드를 강제로 끊지 않고 다음 노드 경계에서 멈추며, 이미 완료된 노드의 보상 작업을 역순으로 실행한다.

**막으려는 문제**: 노드 실행 도중 끊기면 데이터가 반쯤만 반영된 상태로 남는다. 경계에서 멈추면 각 노드는 완료되었거나 시작하지 않은 상태 중 하나다. 이미 완료된 작업은 되돌릴 수 없으니, 역순으로 보상 작업을 실행해 효과를 상쇄한다.

### 엔진: 실행 이력은 롤백되어도 남긴다

**결정**: 배리어 기반 스케줄러로 노드를 실행하고, 노드·묶음 단위로 트랜잭션을 조정하며 재시도한다. 롤백되더라도 실행 이력은 남긴다.

**막으려는 문제**: 실패한 실행의 트랜잭션이 롤백되면, 무엇이 왜 실패했는지에 대한 기록까지 함께 사라진다. 실패 원인을 추적할 수 있는 기록은 업무 데이터와 별도로 남아야 한다.

### 장애 복구: 하트비트 기반 정리

**결정**: 하트비트 기반 정리 작업이 서버 재시작 후 멈춘 실행을 찾아, 시작 시점 버전으로 이어서 실행한다.

**막으려는 문제**: 서버가 재시작되면 실행 중이던 워크플로가 영구히 멈춘 상태로 남는다. 주기적으로 하트비트가 끊긴 실행을 찾아 복구한다. 이어서 실행할 때도 스냅샷 버전을 사용하기 때문에, 그사이 정의가 바뀌었어도 결과가 흔들리지 않는다.

## 다음 과제

- **6주차**: 노드 타임아웃을 트랜잭션 타임아웃으로 정의하는 방식
- **12주차**: 새 트랜잭션을 여는 호출이 커넥션을 두 개 점유하는 문제, 정리 작업과 실행 스레드 간 경합

두 번째 문제는 특히 조심해야 한다. 바깥 트랜잭션이 커넥션을 쥔 채 새 트랜잭션을 열면 커넥션이 하나 더 필요하다. 이런 요청이 동시에 몰리면 모두가 두 번째 커넥션을 기다리며 아무도 첫 번째를 반납하지 못하는 상황이 생길 수 있다.

## 세 명이 동시에 착수하기 위한 협업 규칙

- **소유권**: API는 한 파트가 컨트롤러부터 저장소까지 끝까지 맡고, 각 테이블은 한 파트만 쓸 수 있다.
- **스텁 먼저**: 상대 파트의 인터페이스는 가짜 구현으로 대신해 첫 주부터 동시에 작업한다.
- **계약 우선**: 인터페이스 변경은 별도 브랜치로 기능 PR보다 먼저 머지하고, 제공하는 파트가 계약 테스트를 남긴다.
- **주간 통합**: 매주 예시 흐름으로 "생성 → 배포 → 실행 → 조회" 전 구간을 관통 테스트한다.

## 트러블슈팅: 구현 직전에 발견한 요구사항 해석 차이

**문제**: 팀은 "기존 기능을 지정만 하면 화면에 흐름이 처음부터 만들어진다"고 이해했지만, 설계는 "시작점과 블록만 제공하고 흐름은 사용자가 조립한다"였다.

**발견**: 구현 직전 회의에서 "지정만 해두었는데 기능의 형태를 어떻게 알아내는가?"라는 질문으로 차이를 드러냈다.

**해결**: 요구사항과 구현 범위를 다시 확인해 팀의 방향을 하나로 맞췄다.

구현을 시작한 뒤에 발견했다면 한 파트의 작업이 통째로 버려질 수 있었다. "어떻게 동작하는가"를 구체적으로 묻는 질문 하나가 서로 다른 그림을 드러냈다.
